Alert Operator · Prometheus alert rule inventory

Every alert rule, with an owner and a verdict.

Alert Operator reads what Prometheus actually loaded, joins it with your PrometheusRule objects and grades every rule from Prometheus' own history. One read-only AlertRule per rule says who owns it, whether it runs at all, and whether it can fire, never fires, fires all the time or is always silenced — before the night it was supposed to wake someone.

The problem

After a year, nobody can vouch for the alert rules.

The rules kube-prometheus ships, the ones every Helm chart brings along and the ones teams write themselves pile up. The questions that matter during an incident have no answer anywhere.

Which rules actually run?

A PrometheusRule whose labels miss the Prometheus ruleSelector is accepted by kubectl apply and then silently ignored. The team believes it is covered.

Which can never fire?

The app renamed its metric; the rule still selects the old one. The expression is valid, it matches no series, forever. Nothing complains.

Which are noise, and whose?

The rule that fired 400 times last month, the one that flaps every few minutes, the one silenced 90% of the time — with no team label, no runbook, no severity.

What it finds

Ten findings, each with the reason in one sentence.

Every AlertRule carries its findings in status.findings, most severe first. Inventory findings are recomputed on every change; history findings come from Prometheus every 15 minutes, over a 30-day window capped to its retention. Thresholds are per scope.

Critical

NotLoaded

In a PrometheusRule, but Prometheus does not run it. The usual cause is a label the ruleSelector wants, and the operator names it.

from inventory

LoadError

Loaded, but the last evaluation failed — many-to-many matching, a bad function — or the expression does not parse.

from inventory, history

Warning

DeadQuery

A selector matches no series: the metric was renamed or the exporter is gone, so the rule can never fire.

from history

Noisy

More than 50 activations in the window. Rules like this teach people to ignore pages.

from history

Flapping

More than 10 activations a day that last under 10 minutes each.

from history

AlwaysSilenced

Over 80% of its firing time covered by an Alertmanager silence.

from history

Unowned

No team from the rule label team, or hs/team on the PrometheusRule or its namespace.

from inventory

Info

NeverFired

No activation in the window, for a rule known for 30 days. Fine alone; not next to DeadQuery.

from history

NoRunbook

No runbook_url annotation.

from inventory

NoSeverity

No severity label, or one outside critical, warning, info.

from inventory

How each one is decided, its false positives and the fix: docs/findings.md.

How it works

Read, join, judge, publish. Every 15 minutes.

One AlertScope per Prometheus says where to read and how to judge. Everything else has defaults.

01 · READ

What should run, and what does

The PrometheusRule objects in scope, Prometheus' /api/v1/rules and its retention, and, if configured, Alertmanager's silences. GET requests only.

02 · JOIN

One rule, one identity

Loaded groups are matched to objects by the rule file prometheus-operator writes. A rule on one side only is NotLoaded, or a rule from a plain file.

03 · JUDGE

From Prometheus' own history

Activations, firing periods, empty selectors and silenced time, under a query budget: two queries at a time, 120 a minute by default.

04 · PUBLISH

Objects, metrics, events

An AlertRule per rule, counts per finding and team on the scope, hs_alert_* metrics, and an Event when a rule gains or loses a finding.

When Prometheus cannot be read, nothing is deleted: the scope turns Ready=False, verdicts stay and lastEvaluated stops moving, so stale is visible as stale.

Safety

Installing it cannot break anyone's paging.

It only reads Prometheus and Alertmanager

The clients send GET requests only, a test fails if a write method appears, and redirects are not followed, so credentials never go to another host.

It writes one kind of object

Its RBAC can only read PrometheusRules, Prometheus objects and namespaces; it writes its own AlertRule objects, their status and Events. Secrets only in its own namespace.

Nobody else writes AlertRules

A ValidatingAdmissionPolicy refuses edits by anyone but the operator. A verdict cannot be edited away; fix the rule instead.

It touches only what it created

Objects without its labels are left alone and reported as conflicts; each AlertRule is garbage-collected with its PrometheusRule and never holds it back.

The full list, with the test that enforces each point: docs/safety.md.

Install

Helm, one AlertScope, and the first report card.

Needs Kubernetes 1.30 or later, prometheus-operator's CRDs (for example from kube-prometheus-stack) and a Prometheus the operator can reach. The image and the chart are signed with cosign keyless.

Install guide Release v0.1.0 GitHub
shellfrom charts.hypersurgery.dev
$ helm repo add hypersurgery https://charts.hypersurgery.dev
$ helm install alert-operator hypersurgery/alert-operator \
    --version 0.1.0 --namespace alert-operator --create-namespace
alertscope.yamlwith kube-prometheus-stack as kps
apiVersion: alerts.hypersurgery.dev/v1alpha1
kind: AlertScope
metadata:
  name: main
spec:
  prometheus:
    url: http://prometheus-operated.monitoring.svc:9090
    # with this, a rule that is not loaded comes with the reason
    resourceRef:
      namespace: monitoring
      name: kps-kube-prometheus-stack-prometheus
  alertmanager:
    url: http://alertmanager-operated.monitoring.svc:9093
